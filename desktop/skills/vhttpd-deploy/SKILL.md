# Deploy with vhttpd Desktop

Use the local management MCP. Start with `context_get` and keep the returned `binding_revision` for the rest of the workflow. Call `targets_list` and select a target by its ID. Call `target_status` to check the registered environment, runtime version, readiness, application inventory and known operations. Use `target_applications_list` for live installation IDs and versions and `target_history_list` for known release and upgrade records. `target_diagnostics_get` and `target_logs_query` provide runtime and application evidence after publication. If the host or runtime is disconnected, connect through Desktop. Use the Desktop trust prompt for a first connection.

## Connect a host and manage an environment

Call `targets_list` for saved host IDs. Use `host_connect` for a saved key-authenticated host, confirm in Desktop, and poll `host_operation_get` until completed. Unknown host fingerprints require the existing Desktop trust prompt; password hosts must first authenticate in Desktop. Never send passwords, SSH keys or trust decisions through MCP. Use `host_disconnect` with the current host ID and confirm in Desktop before switching hosts. It closes only the host management connection; remote instances continue running. Unfinished deployment or upgrade operations block disconnect. Repeating a completed disconnect is safe.

If the host is not saved, call `host_register` with a name, SSH host, user and port. Omit `credential_host_id` to use local SSH configuration, or select a saved key-authenticated host ID as the key-reference source. Review the exact endpoint and credential source in Desktop. The tool saves a connection record without connecting or granting host trust. It accepts neither passwords nor private-key paths. Repeating the exact name, endpoint and credential settings returns the same host ID; conflicting existing settings require Desktop editing.

For an existing remote environment, call `environment_discover` on the connected host and select a returned candidate ID. Discovery automatically refreshes Desktop's profile cache; `cached` does not establish live Admin identity or business readiness. Call `environment_adopt_prepare` with host ID and candidate target ID. It requires a running, authenticated Admin endpoint and pins its boot identity and configuration revision. Confirm `environment_adopt_apply` with the returned plan and poll `host_operation_get`. This verifies and saves a connection target without changing remote configuration, ownership markers or processes. Externally managed instances remain externally managed; adoption does not authorize Desktop lifecycle operations. Verify a business listener using `target_request`. If Admin is stopped or identity/configuration changed, inspect the target and prepare again rather than bypassing validation.

Call `host_inventory_get` for installed runtime IDs. To create an isolated environment, use `environment_create_prepare` with host ID, unused name, installed runtime ID, Admin port, and template. The `environment` template exposes only Admin; `vjsx-http` and `vjsx-api` also require a different business port. Review the five-minute plan and call `environment_create_apply` with host ID and plan ID, then confirm in Desktop. Existing directories are rejected rather than adopted. Creation registers and starts the environment.

For a registered managed target, call `instance_status` independently of its Admin API. Use `instance_stop_prepare` or `instance_start_prepare` with target ID; review the environment-wide impact, then call the corresponding apply tool with the returned host ID and plan ID. Configuration or process changes invalidate a plan. Stop sends graceful SIGTERM only to the exact owned process; it never force-kills an arbitrary PID.

Apply returns an accepted operation ID before remote work. Poll `host_operation_get`, retaining that ID even if the request times out. Reusing the current applied plan returns the same operation ID. Prepare a new plan only after checking the previous outcome. A new preparation replaces the previous plan. Operation records are bounded to 128 per Desktop session and do not survive Desktop restart. After reconnect, use host inventory and live instance status to reconcile.

After completion, verify `instance_status`, then use `target_applications_list` and `target_request` for an actual business response. A running process does not establish business readiness. For stop, verify the process is stopped and the test endpoint no longer serves. Keep the original environment and unrelated applications untouched.

## Release an application

For TOML pipeline, WeChat cloud compatibility and Codex Bot, bind the installed component and confirm `app.json` and `component.toml` describe the same source. Choose a test request from the template guide. Inspect the preview for all runtime source and library files. Configure target resources and credentials through Desktop. Check both the business response and the operation record after release and rollback. A first install has no previous artifact. To verify rollback, publish a baseline, publish a second revision to the same installation ID, then roll back the second operation.

1. Call `application_release_prepare` with the target ID and component slot. Omit `installation_id` for a new installation. For an update, use the existing installation ID. Review the version, file actions and restart scope.
2. Call `application_release_apply` with the returned plan ID and confirm in Desktop. Poll `operation_get` with the operation ID. After `completed`, verify the target and make the agreed business request. Use `target_request` with a business listener ID from `target_applications_list` for GET or HEAD verification. Check status and body. The probe bounds the response and preserves redirect status.
3. To roll back, prepare with `rollback_from` set to the current completed release operation ID and omit `installation_id`. Review the recovered version and call `application_release_rollback` with that plan. The previous artifact must still be retained. Verify the business response again.

## Change shared remote routing

Use the local management MCP and confirm the target ID and binding revision. For an existing shared HTTP pipeline with a single-line `match.paths` assignment, call `shared_config_diff` with the pipeline ID and the desired exact paths. Review the relative configuration source and the before and after paths.

1. Call `shared_config_preflight` with the plan ID to compile the whole proposed environment.
2. Call `shared_config_apply` with the same plan ID and confirm the restart in Desktop. Verify both the old and new paths at the business listener.
3. To restore the baseline, call `shared_config_rollback` with that plan ID and confirm in Desktop. Verify both paths again. Keep the same Desktop management session and binding until verification is complete.

If the tool reports a pending restart, check the target state before calling it again with the same plan ID. If the configuration changed since preview, inspect it and prepare a new diff.

## Configure and reclaim an ordinary Relay

Use these ordinary Relay tools through local management MCP; they are separate from public MCP publication tools. Both peers need vhttpd. The Agent initiates a full-duplex WebSocket connection to the Hub. Do not substitute SSH forwarding for the carrier.

1. For a new Hub in an existing registered managed remote environment, call `relay_config_prepare` with target ID, mode hub, a unique Relay ID, an unused high port, carrier path and verification path. Review the returned route. The tool creates one HTTP/WebSocket listener in that environment, generates a carrier token privately, and compiles the whole draft. Specify verify_path only when you intend to expose that HTTP forwarding route to the selected Agent route; omitting it creates only the carrier endpoint. Confirm `relay_config_apply` and poll `relay_operation_get`. This restarts the whole environment, including its other applications. Use the existing-Relay edit workflow below for configurations without the MCP ownership marker; the creation tool does not overwrite them.
2. Call `relay_connection_save_prepare` with a name and verified hub_target_id + relay_id. Alternatively, copy a saved local connection using source_connection_id. Omit target_id for local catalog; specify a registered environment to save to its host catalog. Token and endpoint come from these references; tools accept neither raw tokens nor arbitrary endpoint URLs. Public gateway endpoints and credentials can first be saved in Desktop, then referenced. A loopback-only Hub cannot be turned into a public endpoint by guessing its address. Confirm save_apply, poll the operation and retain connection_id. Saving only changes the library.
3. Call `relay_connection_probe` to verify WebSocket and native authentication. This temporary probe originates from Desktop and closes without replacing the business carrier. A successful probe does not mean the Agent is connected.
4. For the bound local environment, call `relay_config_prepare` with mode agent, the connection ID, matching Relay ID, route and an existing adapter ID. Remote agents use target_id and a connection from that host catalog. Configuration imports an independent credential copy with autostart disabled. Confirm apply and poll. Keep the original config plan ID for recovery.
5. Use `relay_agent_control_prepare` with action start or stop, review the whole-environment restart, and confirm control_apply. The current runtime implements lifecycle by persisting autostart and restarting the selected existing vhttpd instance. Poll the operation, then `relay_runtime_status`. Start is verified only after state registered and a real request through the Hub verification path reaches the expected adapter. Counts are process-wide. After stop, verify the Agent is not registered and traffic no longer reaches the local adapter. Config applies do not increment the source binding generation.
6. To reclaim, stop the Agent, then use `relay_config_restore` with the original agent config plan. It restores exact baseline bytes only while the configuration still matches. Restore the original Hub plan to remove its listener and verification route. Prepare/apply deletion of temporary catalog entries in each scope. Library deletion alone does not remove deployed independent copies.

Plans expire after five minutes before first execution, with up to 64 retained plans and 128 operation records per Desktop session. Reusing a successfully applied current plan returns its operation ID. A restored plan requires a fresh preparation before applying again. After a failed or uncertain publication, query the operation and live state first; do not blindly retry. A plan that already published preserves restore eligibility, including guarded source restoration if its managed runtime is no longer ready. Concurrent source changes block restoration. Never show tokens or full configuration fragments in a report.

## Edit an existing Relay configuration

Use `relay_config_get` to discover existing Relay IDs, safe values and relative configuration sources. Omit target_id for the bound local environment; specify a connected registered environment for remote work. No MCP ownership marker is required. A definition in an include file is edited at that source, without moving it into the root file.

Call `relay_config_edit_prepare` with relay_id, an updates object and/or remove_fields. Updates support mode (hub or agent), carrier (websocket), node_id, path, listener, autostart, max_channels, channel_buffer and reconnect_delay_ms. remove_fields deletes an existing assignment rather than writing an empty/default value; it accepts those fields plus token, url and auth. The same field cannot be updated and removed together. Required-field removal must still pass whole-environment validation. No raw URL, Token or TOML is accepted. Use connection_id to copy private credentials and the Agent URL from a saved native connection with the same Relay ID.

For agent → hub, supply a valid existing listener reference and carrier path, and retain authentication or select a saved credential reference. The preview removes url, autostart and reconnect_delay_ms automatically. For hub → agent, connection_id is required; the preview removes listener, path and auth. Choose autostart explicitly according to the intended outbound connection. These are role conversions over the runtime's WebSocket carrier, not a conversion to an unsupported transport. Review automatic removals and every changed source before applying. References from database exports, takeover adapters or other pipelines can make a conversion invalid; fix those through their own supported configuration workflows rather than bypassing preflight.

A Relay may have disjoint fields across several included TOML files. relay_config_get returns sources and field_sources. Existing fields are edited or removed at their actual source; new fields go into the source containing mode (or the first declaration when mode is absent). No file is consolidated, created or deleted. Runtime support for disjoint Relay fragments is required on both Desktop's bundled validator and the selected target package; older runtimes reject duplicate Relay IDs, so upgrade with the normal reviewed package workflow before using split definitions. Repeated fields are rejected even when equal, including false and zero values. The complete multi-file change uses one Admin changeset.

Review the safe before/after values, relative source, full source revision and restart impact. Call `relay_config_edit_preflight` with the plan ID; it compiles the entire environment through Admin and checks the same boot/source identity. Preparation alone does not authorize apply. Confirm `relay_config_edit_apply` in Desktop and poll `relay_operation_get`. Apply restarts the whole existing environment. Validate both the selected Relay and an actual request through it, then check the environment's other business listeners.

Retain the original plan ID. To recover, confirm `relay_config_edit_restore`, poll its operation and verify the baseline behavior. Restoration replays the exact original source bytes, including comments and credentials, only if the full current configuration still matches the plan. Local and managed remote recovery also support a stopped runtime and included TOML source. Concurrent source edits, a different boot before apply, changed credential references, stale bindings or expired first-use plans require inspection and fresh preparation. Plans and recovery records remain session-scoped; do not restart Desktop before completing recovery.

## Verify a database Relay deployment

For a MySQL Relay binding configured through Desktop, call `relay_database_resources_list` locally and on the connected remote target. Check the local resource, Relay ID, route and remote_resource against the Hub's db-resource export, including its read-only or read-write access. These are configuration identities, not proof of connection. Database credentials remain on the remote host and carrier credentials remain in Desktop configuration.

Use the ordinary Relay status and authentication probe to verify its carrier, then call `relay_database_probe` with the local resource_id. A successful fixed SELECT 1 probe establishes end-to-end connectivity and query execution through the existing vhttpd connection. It never accepts arbitrary SQL, database URLs or raw credentials and does not register another Agent. The debug Skill explains configuration, carrier, transport, database, response and runtime failure stages. A probe does not test application schema or authorize data changes; follow it with the agreed application verification.

Older runtimes report runtime_probe_endpoint_unavailable_upgrade_required. Upgrade using an explicitly reviewed package, retaining the baseline. After validation, restore temporary configuration, stop isolated runtimes and reclaim test database resources. Probe execution itself does not modify configuration or restart the instance.

## Upgrade a runtime

Use `runtime_package_get` to check the local selection before reproducing a target issue. `runtime_packages_list` discovers installed local package IDs, `runtime_package_probe` validates a package against the bound environment, and `runtime_releases_list` queries complete official releases for the desired platform and channel. Use `runtime_download_prepare` with an explicit tag from `runtime_releases_list` and a supported platform. Review and confirm `runtime_download_apply`, retain the operation ID, and poll `runtime_package_operation_get` until completed. The result provides a download ID after SHA256 verification. No arbitrary download URLs or local archive paths are accepted. Downloads last for this Desktop session, expire after one hour and are capped at four per session.

Use `runtime_install_prepare` with that download ID. Omit `host_id` for local installation; for a remote package, connect a saved host of the matching platform and include its host ID. Confirm `runtime_install_apply`, poll the package operation, and verify the returned package ID with `runtime_packages_list` locally or `host_inventory_get` remotely. Installation does not change runtime selection, restart instances or upgrade an existing environment. Prepare/apply plans last five minutes; a new package preparation replaces the previous package plan. A repeated current applied plan returns the same operation ID.

For local selection, first keep the current selected package ID as a recovery target, stop the bound local runtime, and call `runtime_package_select_prepare` with a known installed ID. The tool probes the entire bound configuration and pins its revision and the binary contents. Confirm `runtime_package_select_apply`. Selection clears old change previews and increments `binding_revision`; immediately call `context_get` again, then use the new revision to poll `runtime_package_operation_get`. Check the selected package ID, start the runtime and verify actual business HTTP. To restore the previous local choice, stop, prepare/select the retained baseline ID, refresh context and verify business again. Public Relay grants for the old binding become invalid and must be republished if needed. Remote instance package selection uses the existing upgrade/rollback tools below. Use `host_inventory_get` with a host ID from `targets_list` to distinguish registered targets, discovered environments and the connected host's installed packages. Use `target_status` for the remote package inventory and version. After an upgrade, verify business behavior and use `runtime_diagnostics_get` to inspect the running local reproduction if it differs from the target.

Use `target_status` to choose an installed package ID. Call `runtime_upgrade_prepare` with `target_runtime_id`, review the version and affected applications, then use `runtime_upgrade_apply` and confirm in Desktop. Track the operation with `operation_get` and verify the active package and business behavior.

To return to the previous package, call `runtime_upgrade_prepare` with the current completed upgrade ID in `rollback_from`, then call `runtime_upgrade_rollback` with the returned plan and confirm in Desktop.

## Recover after a failure

For `rolling_back`, keep querying the operation until it reaches a terminal phase. For `rolled_back`, verify that the previous version is serving. For `rollback_failed` or an uncertain submission, retain the operation ID and inspect it before another write. Reconnect the original host in Desktop if needed. Keep credentials in Desktop.
