# Develop a vhttpd application

Choose the development mode in Desktop. For source that has not been installed, stop the current owned runtime and use “打开源码目录（无需安装）…” to authorize an existing folder. It may be empty, contain an existing repository, or contain several project directories. Desktop opens a source workspace connection bound to that folder; no files are copied and no application is installed. Use the Desktop guidance_get(workflow) topic for this binding workflow; develop/vjsx from the selected runtime remain the versioned runtime API references.

Call context_get and send binding_revision with subsequent calls. On the local source connection, source_workspace_get reports the authorized binding and readiness. Through a public Relay, use context_get for the already-bound source; local binding tools are intentionally unavailable there. To choose a project inside the authorized folder, call source_workspace_prepare with a relative directory (dot for the folder itself) and an optional relative TOML entry (default vhttpd.toml). An absent entry or an invalid configuration can be bound for editing; readiness is reported separately. For an entirely empty directory only, template vjsx-http, vjsx-api or environment prepares an initialization preview. A repository containing .git is an existing project: omit template and add the missing files through the revision workflow. Inspect the plan, then source_workspace_bind with its id and refresh context for the new revision. Existing projects stay in place, including their business files and metadata.

Binding and template initialization are separate from changes_validate and actual runtime readiness. A source-only project can edit and restore text files before it has a TOML entry. To run it, create/fix the selected entry using templates_list and target schema, keep includes inside that source directory, provide a local authenticated control listener, validate and start, then check business responses. A component-only configuration may need a local development entry that includes its existing configuration; this does not install the component. Project AGENTS.md is available through guidance_get(project) and the normal text revision tools.

Stop the owned runtime before rebinding or unbinding. Retain each changes record until its edits have been restored or deliberately kept with changes_discard; an unresolved applied record blocks binding changes. source_workspace_unbind changes the binding only and does not delete source files or undo template initialization. Binding changes invalidate old revisions/previews and revoke old Relay publication. Public Relay sessions can edit their already-bound source directory with editing permission, but cannot bind another directory or initialize through the local binding tools; use the normal files/changes workflow in a bound empty directory. Source grants end when Desktop MCP closes; reopen the folder to authorize a new session. Directory traversal, symlinks, concurrent revisions and directory identity changes are rejected. Private files and unsupported file types retain the existing file-tool restrictions.

For an installed component instead, explicitly open a local workspace session for a stopped environment. Call application_templates_list, then application_install_prepare with a component name and template. For an existing component, supply its workspace-relative app.json or component TOML path and retain its application identity. Review the file actions and call application_install_apply with the plan ID. Installation is an explicit alternative to source binding. Remote release still requires the existing independent component/app.json release contract; a source binding alone is not a remote installation.

| Template | Starting point | Local verification |
| --- | --- | --- |
| `pipeline` | `component.toml` declares the listener, path match, pipeline and adapter. Read the target schema for each kind. | GET /healthz returns 200 and pipeline-ok. A path outside the match returns 404. |
| `wechat-cloud-functions` | `cloudfunctions/<name>/index.js` exports `main` and loads the bundled `wx-server-sdk` compatibility API. The client wrapper is in `client/vhttpd.js`. | GET /healthz invokes the bundled hello function and returns its message. |
| `codexbot` | Start at `component.toml` and `app.mts`. Review `config/bot.example.json` for provider instances and startup flags. | GET / returns 200 with `app: codexbot-app-ts`. Verify provider readiness separately when enabled. |

For the WeChat template, `cloud.init`, `getWXContext`, `callFunction`, and supported database and storage operations are implemented in `lib/cloud`. Inspect the bundled implementation for supported options. The health probe uses a fixed diagnostic invocation without a WeChat account. To enable authenticated calls, supply WeChat credentials in the target environment, connect a PostgreSQL or MySQL resource to the engine, and apply the matching bundled schema files. Then verify `POST /auth/login` and `POST /functions/<name>` through the client. For Codex Bot, enable only configured provider instances and keep private overrides in `config/bot.local.json` on the target.

Read the contract for the selected project shape via `guidance_get`: `pipeline` for configuration ownership and route matching, `wechat-cloud-functions` for SDK operations and function loading, or `codexbot` for entry verification and provider readiness. These documents are also shipped in the runtime package's `guidance/` directory. Topic `workflow` returns this development workflow; topics `deploy` and `debug` return the other Workbench references.

Choose the method, path, expected status and response before editing. For application edits, use the following loop.

1. Call `context_get`. Check the selected application, runtime package version, script profile and environment impact. Send its `binding_revision` with subsequent calls. If the binding changes, reread context and confirm the intended application before continuing.
2. Call `capabilities_list` to check which tools are available to this session. On a selected project, set `include_runtime` to `true` to discover configuration domains from the target runtime. Use `schema_get` for a specific domain or kind. Read `guidance_get` with topic `project` for local conventions. For vjsx APIs use `guidance_get` with topic `vjsx` from the selected runtime. When working offline from the matching runtime package, consult `guidance/vjsx.md` in that package. Use `templates_list` to compare runnable HTTP and JSON API templates and `schema_get` for configuration fields.
3. Use `files_list` and `files_read` to find the configured entry and get each file revision. Preserve secret placeholders. Send those revisions to `changes_prepare`, inspect the diff, then call `changes_validate`. A successful configuration check is followed by startup and a business request to verify JavaScript behavior.
4. Confirm the impact before stopping a running shared environment. Apply with `changes_apply` while stopped, then start with `runtime_start`. Over Relay, startup returns `accepted` before warmup finishes. Poll `runtime_status` with the binding revision until `readiness` is `ready`, ending on a failed or stopped phase. Verify the listener, status code and response using `application_request`. Keep the restore record until verification passes.
5. On startup or response failure, inspect `logs_query`, stop the runtime if it is running, call `changes_restore`, then restart and verify the baseline. If a file revision conflicts, reread it and prepare a new diff. Restore records belong to the current Desktop session.
