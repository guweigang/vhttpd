# vhttpd 本地开发工作台设计

## 1. 目标与设计状态

本方案根据 2026-10-14 的产品讨论整理。已确认的方向是：使用 V / ui2 构建本地宿主，第一版通过系统默认浏览器打开 Admin UI；vjsx 在被管理的 vhttpd 实例中执行项目代码。本文定义职责、MVP 范围和验收要求。2026-10-17 已交付 macOS 宿主原型、HTTP / JSON API 项目创建、实例启停与切换、浏览器自动登录、项目配置 / Relay 概览和系统文本编辑器入口；Admin UI 已增加基于真实快照的 Relay 运行态视图。SSE 模板、专用请求测试器和正式打包仍按后文分阶段推进。

本轮验证包括配置 include 解析与脱敏测试，以及本机 hub / agent 的 registered → backoff 状态变化。宿主概览读取磁盘配置，Admin UI 展示实例状态；二者不会互相覆盖配置。

目标是让开发者完成“选择项目 → 配置入口与处理逻辑 → 启动 → 测试 → 查看结果 → 修改并再次验证”的本地闭环，并让项目配置和源码可以继续用于服务端运行。

第一版选择最小架构：宿主拥有项目和进程控制界面；浏览器中的 Admin UI 管理已运行的实例。实例停止后，用户回到宿主重新启动。浏览器内启停、常驻宿主 HTTP 服务与嵌入 WebView 均不属于第一版。

## 2. 现有基础与新增工作

现有 Web 管理界面包含仪表板、应用、编辑器、运行时图、Schema、草稿和事件等入口，其静态资源与实例控制平面组合方式见 [Web 管理界面](./Web%20管理界面.md)。第一版复用现有界面和 Admin API，而不是建立独立配置系统。

以下是本次源码核查的依据；“已有”只表示存在代码或测试，尚未进行桌面端运行验证。

| 基础能力 | 依据 | MVP 处理方式 |
|---|---|---|
| Admin UI 页面与导航 | [页面源码](../../admin/ui/index.html) | 复用并补充本地项目提示 |
| 配置及源码草稿、校验、发布、运行计划替换接口 | [Admin 路由](../../src/admin_server.v) | 复用现有接口；明确磁盘发布与运行生效的区别 |
| v2 listeners、engines、adapters、pipelines、resources 配置模型 | [v2 配置结构](../../src/config/v2_config.v) | 界面映射现有模型，具体组合以运行时校验为准 |
| 嵌入式入口、模块目录、构建目录、能力开关 | [嵌入式运行配置](../../src/config/embedded_host.v) | 显示入口与目录，复用解析逻辑 |
| vjsx 源码签名变化后重建执行器的测试 | [执行器测试](../../src/inproc_vjsx_executor_test.v) | 验证当前更新语义；不承诺所有场景无缝热更新 |
| 本地桌面宿主与进程管理 | 本方案新增 | 实现 ui2 宿主及生命周期管理 |

ui2 的平台编译、控件表现、退出行为与打包方式必须在原型阶段验证。浏览器方案避免让第一版依赖嵌入 WebView；具体平台交付能力仍需要宿主和 vhttpd 二进制共同验证。

## 3. 架构

```text
用户
 ├─ ui2 宿主窗口
 │    ├─ 项目登记、配置路径、工作目录
 │    ├─ 二进制检查、启动、停止、重启
 │    ├─ 进程状态、启动日志
 │    └─ 打开系统浏览器 / 外部编辑器
 │              │ 启动与监督
 │              ▼
 │         vhttpd 实例
 │          ├─ Admin UI 静态资源 + Admin API
 │          ├─ 输入、路由、pipeline、资源、输出
 │          └─ vjsx 执行器 → 项目 JS/TS 逻辑
 │
 └─ 系统浏览器 → 当前实例的 Admin UI → 当前实例的 Admin API
```

MVP 中，浏览器不直接访问宿主的文件系统或进程控制能力；宿主不提供给浏览器调用的控制 API。宿主关闭与浏览器关闭是两件独立的事。

宿主维护所启动进程的身份和状态；Admin API 描述实例内部的配置与运行状态。宿主无需理解每条 pipeline 的业务语义。

## 4. 职责边界

### 4.1 ui2 宿主

宿主负责本机环境及被管理实例的进程生命周期：

- 注册已有项目，以及从受维护的模板创建项目。
- 记录项目根目录、配置路径、工作目录、二进制路径和可选环境文件路径。
- 检查二进制版本、文件存在性、模板所需运行环境和管理地址。
- 启动、停止、重启本工具拥有的 vhttpd 实例。
- 捕获标准输出、标准错误、退出码和启动失败原因。
- 在确认实例就绪后打开 Admin UI；提供再次打开按钮。
- 打开项目目录和外部编辑器。
- 处理宿主退出时所拥有实例的收尾。

宿主不实现协议转换、不执行项目 vjsx、不复制 vhttpd 配置编译器，也不负责编辑器中的业务代码语义。

### 4.2 Admin UI 与 Admin API

Admin UI 负责实例内的配置与调试体验，后端操作由 Admin API 完成：

- 展示输入监听、路由、处理逻辑、资源、上游连接和输出行为。
- 按支持的 Schema 配置执行器与 pipeline。
- 编辑配置草稿，展示校验结果和差异，发布到指定配置文件。
- 区分“草稿”“已写入文件”“运行中已生效”。
- 展示应用状态、运行拓扑、运行时事件和协议错误。
- 提供 MVP 模板所需的请求测试和结果展示。
- 展示 vjsx 入口、模块目录及加载错误；已有源码编辑能力可以保留。

实例停止后 Admin API 不可用，刷新页面也可能失败。这是 MVP 的明确边界。页面在检测到连接断开时停止无意义的重复请求，并提示“实例连接已断开，请在本地宿主中检查或重新启动”；不得把所有连接断开都判定为进程已停止。

第一版不在 Admin UI 放置整进程启停按钮。现有 worker 重启等实例内部管理动作与整进程控制分开表达。

### 4.3 vjsx

vjsx 负责运行项目的 JS/TS 处理逻辑：

- 接受 vhttpd 分发的请求或事件。
- 执行项目处理函数并返回运行时支持的响应或结果。
- 按 vhttpd 的运行配置使用资源与能力。
- 由现有执行器生命周期管理加载、变更检测、重建和关闭。
- 将错误交给运行时诊断与日志通道。

vjsx 是实例内部的执行能力，不是桌面宿主的扩展语言。项目代码不得因为从桌面工具启动而自动获得宿主的项目注册、进程管理或任意文件操作接口。

文件、网络和进程等能力开关沿用运行时配置；这些开关不应被宣传为已经证明完备的安全沙箱。MVP 以用户自己的本地项目为使用范围。

### 4.4 职责矩阵

| 操作 | ui2 宿主 | Admin UI / API | vjsx |
|---|---|---|---|
| 项目登记、目录选择 | 执行 | 无 | 无 |
| 整个实例启停 | 执行 | 显示连接状态 | 随实例启动与关闭 |
| input / output、路由、pipeline 配置 | 提供项目定位 | 编辑、校验、发布 | 执行其中的应用逻辑 |
| 配置解析与编译 | 调用已有能力 | 调用已有能力 | 不负责 |
| JS/TS 编辑 | 打开外部编辑器 | 保留现有编辑入口 | 不负责编辑 |
| JS/TS 加载与执行 | 不执行 | 展示状态与错误 | 执行 |
| 启动失败及进程退出日志 | 采集、展示 | 在线时可显示运行时诊断 | 产生运行错误 |
| 本地进程身份 | 权威来源 | 不推断 | 无 |
| 当前生效配置及逻辑状态 | 不自行推断 | 从运行时读取 | 提供执行侧状态 |

## 5. 项目、配置和状态

### 5.1 项目模型

建议由宿主持久化下列项目登记信息；这是宿主元数据，不是第二份运行时配置：

| 字段 | 含义 |
|---|---|
| project_id / name | 稳定标识与显示名称 |
| root_dir | 项目根目录 |
| config_path | 项目实际 TOML 入口 |
| working_dir | 启动时工作目录 |
| binary_path | 所使用的 vhttpd 二进制 |
| env_file_path | 可选本地环境文件路径 |

默认采用项目根目录作为工作目录，尊重现有路径解析规则。管理地址从有效配置解析，不能只靠文本搜索 TOML 字段；若目前缺少可复用的配置检查输出，应先补充机器可读检查接口。

宿主登记可包含多个项目，MVP 限制同时运行一个受管理实例。切换项目时先停止当前实例；多实例并发管理后续扩展。

### 5.2 单一配置来源

项目 TOML 与源码是可迁移的应用来源。Admin 草稿是编辑过程状态；运行计划是运行时状态；宿主只持久化启动与项目定位信息。

宿主默认不通过隐式 CLI 参数覆盖用户正在编辑的协议、路由、执行器配置。必须覆盖的管理绑定或认证参数需要明确展示其来源及优先级，避免文件内容与生效配置不一致。

配置应用分为两个阶段：

1. 现有 Admin 工作流完成草稿校验、差异查看与文件发布。
2. 已支持且验证过的变更使用现有运行计划应用流程；其余变更标记“待重启生效”，由宿主执行重启。

第一版不新增通用热更新机制。运行计划替换接口的存在不等于全部配置均可无中断应用。

### 5.3 配置文件变更冲突

外部编辑器与 Admin UI 可以修改同一项目。发布前检查原始文件版本；文件已经改变时拒绝直接覆盖，提示重新读取并检查差异。宿主不做后台配置同步写入。

移除宿主中的项目登记不删除项目目录或源码。

### 5.4 Relay 归属于项目运行计划

以现有代码归属为准：Relay 声明来自项目 TOML 的 `relays`，经配置编译进入该项目的 RuntimePlan，再由实例建立连接、通道与会话。agent / hub 是运行角色，local / remote 只是节点部署位置，不新增工作台全局开关或第二份连接配置。

| 层级 | 职责 |
|---|---|
| 项目 TOML | 声明 Relay 的角色、carrier、URL / listener、节点标识、认证引用、重连参数及关联 pipeline |
| ui2 宿主 | 从同一配置编译器读取项目概览，展示 agent / hub、脱敏地址、关联 pipeline，并打开配置和源码 |
| Admin UI / API | 编辑和发布项目配置；从实例运行时读取 agent 状态、连接尝试、错误、carrier、channel 与 session |
| vhttpd Relay 运行时 | 认证、连接、重连、帧分发与生命周期管理 |
| vjsx | 仅执行项目 pipeline 中被分发的业务逻辑 |

依据为 [项目配置编译](../../src/config/v2_plan_compiler.v)、[Relay 运行时](../../src/relay/runtime.v)、[Admin 运行时快照](../../src/admin_runtime_context.v)及现有 [agent 示例](../../examples/config/relay-agent-local-v2.toml)、[hub 示例](../../examples/config/relay-hub-v2.toml)。

宿主中的磁盘配置概览不能称为连接成功，也不能代替实例的生效配置。管理员在 Admin UI 校验、发布，再由宿主展示生效状态并执行重启及自动复查。跨项目可复用参数目前可通过已有 include 与环境引用机制组织；若以后出现共享连接档案的实际需求，再单独设计其引用、凭据和覆盖优先级。

已交付项目配置 / Relay 概览、系统文本编辑器入口和 Admin UI Relay 运行态视图。Admin UI 的 Relay 表单支持在 v2 项目主配置及任意层级的 include 文件中新建、编辑 agent / hub、连接 URL / WebSocket listener、节点、Token 或环境引用、自动连接与通道参数，并把整个项目任意来源文件中的 Pipeline 绑定为 Relay 入站或出站。出站使用每条 Pipeline 独立的 relay-delivery adapter，指定远端 Pipeline ID；其他 match、transforms、policies 与未编辑的 TOML 保留。

编辑流程为：载入配置来源 → 保存草稿并校验 → 查看来源文件 TOML 与整个项目的运行计划差异 → 发布到原来源文件 → 检查整个项目的生效状态。配置加载器递归枚举主配置和 include，界面显示文件路径、直接包含它的上级文件及其 Relay 标识；同名来源文件使用不同草稿标识。

草稿绑定项目入口与一组来源文件，记录每个文件的原始文本和候选文本。Relay、Pipeline、Adapter 可以分别来自不同 include；界面列出整个项目的入站 / 出站绑定、每个组件的来源和远端 Pipeline ID，Pipeline 下拉框覆盖整个项目。新建出站 Adapter 默认写入 Pipeline 的来源文件；已有独立 Adapter 保持来源，若被其他 Pipeline 共享则为当前 Pipeline 单独生成，避免影响其他绑定。

校验和差异预览在内存中同时替换全部候选文本，复用正常的 include 合并、相对路径、循环及重复定义检查，再编译完整 RuntimePlan；不先写入项目配置。来源可以是不含 version、listener 或 Adapter 定义的片段，引用由其他文件提供。

发布复用 Admin 状态存储的目录锁：检查全部来源是否仍属于项目、是否与草稿的原始文本一致，整项目预校验通过后先暂存所有文件，再逐一替换并执行整项目后校验。暂存文件使用独占创建并保留来源权限；普通写入或后校验失败会回滚本次已提交的文件，回滚失败单独报告。这是进程内失败补偿，不承诺跨文件的崩溃恢复。

只有草稿涉及的来源文件被修改，其余文件和 include 结构保持原样；已脱离项目的来源、重复来源、外部冲突和任意另存路径会被拒绝。运行计划预览、应用和生效检查始终使用项目主配置路径。表单修改会使先前整组校验失效，未校验不能发布。

Relay 编辑页只负责编辑、整项目校验和发布，发布后引导用户返回宿主工作台；不再提供运行计划应用或生效检查按钮。宿主在后台每 2 秒通过本次启动的临时凭据读取主配置的运行计划差异，并在项目列表标记“配置待生效”，在当前项目显示有差异的 Relay、Pipeline 等组件。所有尚未生效的变更在此工作台流程中由宿主重启处理；底层运行计划应用 API 保留原有能力。

宿主启动或重启后，在认证就绪时立即自动检查，只有主配置编译成功且与运行计划没有待执行差异才显示“项目配置已生效”。认证失败、接口不可达、响应异常或配置无法编译均显示检查失败并自动重试，保留此前待生效记录；停止的项目显示待启动检查，不把历史成功当作当前运行成功。状态缓存按项目路径隔离，仅保留在本次工作台会话中；MVP 仍只运行一个受管理实例，不探测或接管其他进程。

宿主提供“差异详情”：以启动时及后续确认已生效时的来源文件指纹为基线，列出修改、新加入和移出项目的主配置 / include 文件，同时展示运行计划确认的受影响 Relay、Pipeline 及其来源；未修改但受影响的组件来源另列。字段详情按整项目编译后的 Relay / Pipeline 结构比较，显示字段名、修改前后的值、新增 / 移除 / 修改及配置来源；包含 Relay 选项、Pipeline 的 ingress / egress、match、transforms、policies，以及关联出口 Adapter 的选项。仅被依赖变更影响而自身字段未变的 Pipeline 单独说明，避免把影响关系当作字段修改。组件移动来源时显示来源前后的变化。

宿主的字段展示基线只缓存脱敏后的字段显示值、组件标识和比较指纹。恢复另需原始 TOML：宿主 worker 在整项目确认生效后，将主配置和全部 include 的内容、权限、来源索引及确认时间保存到项目本地版本历史。按用户当前取舍，移除加密与系统钥匙串依赖，使用普通 JSON 文件保存完整配置原文；目录权限 0700、文件权限 0600。历史位于当前用户 Application Support/vhttpd-workbench/recovery 下，以项目配置路径和工作目录区分，采用文件锁、原始文件校验和独占暂存后原子替换，避免并发或失败写入覆盖历史。每项目最多保留最近 20 个版本，整个历史文件最多 16 MiB，超出时移除最早版本；单个版本仍过大则保留旧历史并报告保存失败。只在整项目确认生效且内容或来源权限变化时新增记录，轮询不重复记录；回滚后确认生效会追加新记录，不改写旧记录。读取失败保留原文件，界面和日志不输出配置原文。退出重开、项目尚未启动或当前 TOML 已损坏时，也可从历史预览并恢复；离线恢复先报告整项目校验结果，启动后再检查实际生效。之前的加密快照文件保留但不再读取或自动迁移，新历史从下次确认生效开始记录。token、password、secret、API key、Authorization、Cookie 等按敏感字段处理；URL 的用户信息、查询参数与片段隐藏，匹配条件的查询值、自定义请求头及不明确用途的字符串选项采用隐藏显示。敏感值更换即使两侧均为“已脱敏”也标记变化，清空与未定义分开显示。对敏感值的比较使用每次启动独立密钥的指纹，指纹不进入界面状态、日志或链接。字段基线随整个项目确认生效后更新，重启后清空已生效差异。检查失败时保留上次成功的详情并明确标注；若只有环境引用或运行计划发生变化，说明文件文本未变，不伪造文件修改。

工作台以“选项目、启动、打开 Admin UI、配置、检查生效”为主线，不要求用户理解版本 ID、密钥管理或进程通信。已有历史时从项目工作台直接进入“版本历史”，按确认时间倒序显示版本号、最近生效标记和配置来源数量。每个版本提供“查看变化”“恢复此版本”；默认以上一已生效版本为对比基准，也可指定任意另一版本。版本对比页直接标明可恢复的版本号，当前已生效且文件一致的版本不重复提供恢复操作。恢复完成后，如项目未运行或仍有运行差异，结果页直接提供“启动并检查”或“重启并检查”，减少返回层级。对比只在内存中编译两份历史配置，展示来源文件及 Relay / Pipeline 字段的脱敏变化，不改写当前项目。恢复目标与最近生效基线分别保存，选择旧版本不会修改最近生效记录。

宿主的版本历史提供“预览回滚”：对所选版本的主配置和全部 include 做整项目校验，列出恢复文件、include 关系及脱敏后的字段当前值 / 恢复值；预览本身不写入文件。用户点击“恢复这份预览”后，在与 Admin 发布共用的存储锁内重新检查全部预览输入和目标计划，暂存所有来源后统一恢复，并再次编译整项目及查询运行计划确认生效。预览后发生外部修改时拒绝覆盖；普通写入或校验失败会撤回本次已写入的文件，撤回失败明确报告。已缺失的旧来源可重新创建，已移出的旧 include 可重新接回；新增来源从 include 关系移出但保留文件。不承诺跨文件崩溃恢复。当前配置损坏时仍可预览文件并恢复合法目标；恢复成功但仍有运行差异时显示待生效，由宿主继续重启和检查。

每个仍属于项目的来源都有“在 Admin UI 继续编辑”入口，复用一次性 POST 登录交接，URL 只携带项目与来源标识。含 Relay 声明的文件进入该来源的 Relay 表单，其他 TOML 来源进入配置草稿。宿主打开前和 Admin UI 落点时均检查项目及 include 成员关系，已移出的来源禁用编辑。重启及生效检查继续归属宿主，浏览器不获得进程控制能力。include 中的标准 Relay 表定义支持表单编辑；复杂内联 / 多行字段继续使用现有 Editor 编辑。

验证覆盖无效引用拒绝、保留未编辑 TOML、入站 / 出站绑定、发布后尚未生效，以及本机 Hub / Agent 重启后 registered 和真实 HTTP 接力响应。查看配置不会自行建立远端连接或改写 TOML。

## 6. 启动、停止与恢复

### 6.1 启动流程

1. 用户选择项目并点击启动。
2. 宿主解析配置、检查二进制与所需文件，确定管理地址和环境。
3. 用参数数组创建子进程，设置工作目录和环境；不拼接 shell 命令。
4. 保留进程句柄、启动身份和输出日志，进入 starting。
5. 在有限时间内确认进程存活，并通过带认证的 Admin 请求确认目标实例就绪；仅端口连通或匿名 health 成功不足以证明身份。
6. 成功后进入 running，打开系统默认浏览器中的 Admin UI。
7. 失败后保留日志、退出码和明确原因；不打开无法使用的页面。

预检查端口不能排除启动竞争；最终以真实启动结果为准。管理地址发生冲突时报告错误，不自动修改用户项目配置。

宿主每次启动使用临时 Admin token 验证实例身份。浏览器登录使用 30 秒有效的一次性票据，经本地临时页面 POST 兑换 HttpOnly、SameSite=Strict 会话 Cookie；管理 token 与登录票据均不进入 URL，页面不再持久化 token 到 localStorage。票据只能兑换一次，重启实例使旧会话失效。

### 6.2 首次使用的操作闭环

2026-10-18 从新用户视角完成实际桌面和浏览器验证，并收敛为以下流程：

1. 在宿主新建项目，选择 HTTP / JSON API 模板和目录；默认勾选“创建后立即启动，并打开浏览器 Admin UI”，一次操作完成创建、登记、启动与自动登录。
2. Admin UI 顶栏“编辑项目配置”直接进入常用表单：按“HTTP 监听 → HTTP 路由 → vjsx 执行器 → 出口 Adapter”排列，编辑已有 HTTP/TCP 数据监听的地址和端口、路由路径 / 方法 / 输入监听 / 出口 Adapter，以及 vjsx 的 JS/TS 入口和模块目录。每项显示原配置来源，跨 include 绑定可选择项目已有组件，管理监听不在常用表单中编辑。表单只改变化的字段，保留其他配置、注释、路由顺序及来源文件；未明确配置的默认值不冒充已填写值。复杂字段或嵌套路由表引导使用“高级：编辑此来源 TOML”，原始编辑器仍留在同页。宿主配置来源链接优先进入可编辑的常用表单，含 Relay 的来源仍进入 Relay 表单。修改入口路径不会自动生成或修改 JS/TS 文件，路径解析与入口有效性由现有后端及启动流程处理。
3. 修改后点击“保存并校验”，把所有变化的来源文件作为一份项目 changeset 草稿保存，再按主配置入口编译完整配置，差异也基于整项目。只有当前表单通过校验才允许发布，再次编辑立即使校验失效；发布前仍核对每份原始文本，发现外部修改时拒绝整组覆盖并提示重新读取。重新读取有未发布修改时明确确认，普通页面切换保留表单。原始 TOML 编辑继续使用对应来源草稿。技术结果默认折叠，不在表单直接输出包含敏感配置的完整 TOML。
4. 点击“发布配置”后明确提示文件已发布，回工作台点击“重启并生效”。工作台每两秒更新待生效状态，项目页直接提供该按钮，无需先进入差异详情。
5. 重启结束后自动按整个项目检查，确认后显示“项目配置已生效”。重启不自动再开浏览器标签；需要继续浏览器编辑时使用工作台“打开浏览器”重新登录，重启后的旧会话失效语义保持不变。

常用表单支持新增 HTTP/TCP 监听和 HTTP 路由：先选择项目已有的主配置或 include 来源文件，再填写 ID、地址 / 端口或路由条件与绑定；新增卡片也可调整来源。ID 在整项目中检查重复，包含常用表单未展示的管理监听和其他 pipeline。监听与路由可写入不同 include，新路由可以选择在目标文件的某条既有路由之前插入或追加到末尾，默认位于该文件第一条路由之前，保留其他路由的相对顺序。跨文件顺序沿用项目 include 的合并规则；端口建议只避开配置中已有端口，实际绑定由启动检查确认。

vjsx 执行器和出口 Adapter 也可选择项目已有的主配置或 include 文件新增，卡片中可调整 ID 和来源。执行器填写已存在的 JS/TS 入口和可选模块目录，新增默认使用 script 运行模式，不生成源码。出口提供执行器处理（http-handler）、静态文件（static）、固定响应（fixed-response）和 Relay 转发（relay-delivery）四种常用类型；其他类型的参数继续使用高级 TOML 编辑。新增出口默认选择最近的可用 vjsx 执行器，新增路由默认选择最近的可用出口；尚未发布的组件可直接跨文件绑定，修改新组件 ID 会同步更新表单中的绑定，ID 仍按整个项目所有同类组件查重。

删除前显示来源文件、受影响的输入 → pipeline → 出口 / Relay 绑定，以及项目内引用的字段与来源。执行器的预览也追踪 Adapter、transform 引用到受影响的 pipeline。监听或出口仍被 HTTP 路由引用时，用户需明确勾选一并删除这些路由；非 HTTP pipeline、共享 Adapter、transform 等其他引用须先改绑或先暂存删除对应组件，不能自动级联删除。无法在表单确定的动态执行器引用也会阻止直接删除，交由高级编辑和整项目校验处理。删除路由会展示其出入口及指向它的项目引用。删除、取消新增和级联均先暂存在表单中，发布前可以逐项撤销；尚未处理的引用会阻止生成发布草稿，整项目编译仍是发布前的最终校验。监听、执行器和出口的从属子表及跨来源扩展随声明一起移除，未选择的组件和源码保留；复杂路由表继续使用高级 TOML 编辑。所有变化作为同一个 changeset 按原来源文件统一校验、检查外部修改并发布，随后由 ui2 宿主重启和按整项目检查生效。

空项目列表提供新建及导入入口；创建成功会关闭旧项目的历史、回滚、差异和详情视图，直接显示新项目工作台。Admin UI 继续只负责配置编辑、校验及发布，宿主负责重启与生效检查。

### 6.3 进程状态

```text
stopped → starting → running → stopping → stopped
             │         │
             └─────────┴─→ failed
failed → starting（用户再次启动）
```

running 状态另显示 Admin 可达性：正常、暂时不可达、认证失败。接口异常不应直接触发重启。

启动、停止、重启操作串行执行，执行期间禁用重复按钮。重启必须等待旧进程完成退出，再启动新进程。

### 6.4 停止与退出策略

- 先通过平台支持的方式请求正常关闭，等待退出期限。
- 超时后显示仍未退出的状态，允许用户明确选择强制结束。
- 只能结束宿主所拥有的进程及经验证的子进程；不得根据端口或进程名杀掉其他实例。
- 必须验证各平台的子进程和 worker 收尾，避免退出后残留进程。
- 关闭浏览器不停止实例。
- 退出宿主时默认正常停止其拥有的实例；第一版不提供后台遗留进程模式。

宿主意外退出时，重新启动不能仅凭保存的 PID 接管或终止进程，应核验身份。无法核验的实例标记为可能残留并提供诊断；自动接管不属于 MVP。

## 7. vjsx 开发工作流

第一版优先采用外部编辑器。项目模板生成可运行的 JS/TS 入口和对应 TOML，宿主提供“打开项目”入口，Admin UI 展示入口路径、资源绑定、请求结果与错误。

已有源码草稿接口可用于浏览器编辑，但不要求第一版新增完整 IDE、语言服务、断点调试或文件管理器。

执行器预热按阶段限时：模块与编译运行时初始化最多 30 秒，初始化完成后，业务启动钩子单独保留 10 秒限额。初始化失败立即返回，不等待下一阶段；超时取消对应任务，错误区分模块初始化与启动钩子。这样避免冷启动消耗掉业务钩子的全部时间，同时仍限制挂起的代码。管理 API 可达只证明管理面就绪；发布、重启回归须同时检查真实业务 HTTP 响应与整项目运行计划，不能仅凭管理接口成功或磁盘配置一致宣布业务可用。

修改后的状态必须区分：

| 状态 | 含义 |
|---|---|
| 源码已保存 | 文件写入成功 |
| 等待加载或待重启 | 尚未证明运行中的执行器已使用新代码 |
| 已验证生效 | 运行时证据或测试请求确认新行为 |
| 加载或执行失败 | 显示错误，提供修复与宿主重启路径 |

源码签名更新不自动证明所有执行 lane、生命周期钩子和长连接都已经切换到同一版本。源码监测、重建以及失败后的具体行为需要依据当前实现验证；缺少可靠生效状态接口时，UI 不显示未经证实的“热更新成功”。

MVP 必须保证修改源码后能够通过明确重启再次运行。已存在的自动更新能力可以保留，但不作为无中断更新、旧状态保留或失败自动回滚的产品承诺。

## 8. input / output 的产品表达

界面用“输入 → 处理 → 输出”帮助用户理解配置，同时映射现有 listeners、engines、adapters、pipelines 等模型。

MVP 只暴露模板已经验证的配置组合：

- 输入：本地 HTTP 监听与路由。
- 处理：vjsx 入口，以及需要时的现有 pipeline 配置。
- 输出：普通 HTTP 响应；第二个模板提供 SSE 输出。
- 资源与能力：模板实际需要的配置项，并提供原始 TOML 编辑入口。

HTTP 响应、SSE 和 provider 消息发送具有不同语义，不能承诺通过任意两个协议下拉框就可完成转换。WebSocket、MCP、飞书等现有能力仍可通过高级配置使用，但其新手配置向导和专用测试器不属于 MVP 验收范围。

## 9. 第一版 MVP

### 9.1 必须交付

| 功能 | 最小交付标准 |
|---|---|
| ui2 宿主窗口 | 项目列表、当前项目、状态、启动/停止/重启、打开 Admin UI |
| 项目创建与导入 | 一个 vjsx HTTP 模板、一个 SSE 模板；导入已有项目；不覆盖非空目录 |
| 环境检查 | 二进制与版本、配置和入口文件、管理地址、明确的启动错误 |
| 进程监督 | 单个活动实例、串行生命周期操作、退出码、启动日志、退出收尾 |
| 浏览器打开 | 等待认证就绪后打开默认浏览器；支持再次打开；无需 WebView |
| Admin 配置闭环 | 入口、路由、监听配置，校验、差异、发布，明确生效或待重启状态 |
| vjsx 开发闭环 | 外部编辑器入口，修改源码，重启，再次测试和显示错误 |
| 最小请求测试 | 普通 HTTP 结果；SSE 增量输出与取消，支持模板所需请求参数 |
| 配置与认证边界 | 项目配置单一来源，管理面本机绑定，token 不进入 URL 或日志 |
| 独立运行 | 项目可以脱离宿主，直接由 vhttpd 命令行启动 |

请求测试如由浏览器直接调用数据端口，需要明确处理跨源访问；若复用受认证的 Admin 测试转发，则仅允许当前项目明确配置的目标，不开放任意 URL 代理。采用哪种方式在原型阶段确定并记录。

### 9.2 不纳入第一版

- 嵌入式 WebView 和原生控件与网页混排。
- 浏览器直接启动、停止或重启整个实例。
- 常驻宿主 HTTP 服务、浏览器与宿主的 RPC 桥。
- 多实例并发、远程服务器管理、自动接管已有进程。
- 自动安装依赖、自动更新二进制、自启动和后台常驻模式。
- 托盘作为必须交付功能。
- 完整 Web IDE、断点调试、可编程宿主插件。
- 所有协议的配置向导、通用协议转换器。
- 全部配置热应用、源码更新事务、失败自动回滚。
- 云同步、账号系统及远程发布。

## 10. 最小安全与认证要求

管理面和模板的数据监听默认绑定 loopback，是否开放数据端口由用户显式配置。导入已有项目时显示管理绑定与认证状态；MVP 的本地管理模式要求非空认证和本机管理绑定，不能静默改写现有文件。

宿主只操作已选择的项目和其拥有的进程。项目根目录外的配置 include 或源码依赖需要明确显示；文件写入范围不能因为 UI 输入了一个路径而无限扩大，需处理真实路径、符号链接与目录穿越。

秘密值沿用现有环境引用机制，UI、版本比较和日志对秘密脱敏。按当前用户要求，历史文件不加密，原配置中直接填写的 token 等值会随完整版本保存在本地 JSON 中，由当前用户的目录及文件权限限制访问；不引入钥匙串、密钥或授权流程。环境引用保留引用文本，不额外复制环境变量或环境文件中的秘密值。

Admin API 的文件发布与源码权限沿用后端约束；本地启动不能绕过认证或扩大原有权限。

## 11. 实施顺序与验收

### 阶段 A：宿主可行性原型

验证 ui2 窗口、目录选择、子进程管理、日志展示和浏览器打开。macOS 作为首个验证平台；Windows、Linux 逐个平台验证与交付，不因框架覆盖某个平台就声明整个产品已支持该平台。

验收：从宿主启动一个现有项目，确认正确实例就绪后打开 Admin UI；停止实例后宿主保持可用并可再次启动。

### 阶段 B：项目与配置体验

加入两个模板、项目登记、环境检查、认证流程和配置生效提示。复用现有 Admin 草稿与运行计划能力。

验收：新用户从模板创建项目，在 Admin UI 修改一个配置项，完成校验和发布，并能判断是否需要在宿主重启。

### 阶段 C：vjsx 开发闭环与打包

补齐外部编辑器入口、HTTP/SSE 测试、源码更新提示与错误展示。验证受支持平台的安装包、静态 UI 资源定位和进程收尾。

验收用例：

1. 空白环境安装后，选择模板，启动并看到预期响应。
2. 修改 vjsx 返回内容，明确重启后测试得到新内容。
3. 配置错误、入口缺失、认证错误和端口冲突均有可理解的提示。
4. 运行中出现源码加载错误，保留可用诊断；修复后能够恢复。
5. SSE 逐步输出，并能取消请求，验证实际连接清理。
6. 停止或崩溃后宿主仍可用，不错误显示“运行中”。
7. 连续点击启动/重启不创建重复进程；退出宿主后不残留其拥有的 worker。
8. 外部修改文件后，Admin 发布不静默覆盖。
9. 关闭浏览器后实例继续运行；停止实例后浏览器显示连接失效提示。
10. 项目脱离宿主以命令行启动时，配置与逻辑行为一致。

## 12. 后续演进

浏览器内启停若成为实际需求，再引入独立常驻宿主服务，提供项目限定的进程控制 API，并让控制页面独立于目标实例存活。该阶段需明确认证、Origin 校验、静态页面服务与实例 API 路由。

嵌入 WebView 时替换展示容器，保留项目、进程管理和 Admin API 的职责。宿主扩展语言、无中断源码更新和多实例管理分别设计，避免与展示容器一起耦合。

第一版的成功标准是完整跑通本地开发闭环，而不是覆盖所有配置字段。评估首次成功耗时、失败诊断是否清晰、用户是否能够独立修改并再次验证。
